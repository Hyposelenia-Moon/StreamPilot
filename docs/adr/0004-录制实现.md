# ADR 0004：原始流录制、自动分片与断流重连

- 状态：已接受
- 日期：2025-02-14
- 相关文档：`0003-解析器实现.md`、`0005-桥接与打包.md`

## 背景

需求（第 3.3 节）要求：

- **原始流录制**：不转码、不重新编码，直接保存平台原始流；
- **自动分片**：按文件大小或时长自动切分；
- **断流重连**：主播短暂断流后自动重连；
- **元数据记录**：主播名、房间号、标题、开播时间、录制时长；
- **文件命名**：`{主播名}-{房间号}-{开始时间}-{分片序号}`，扩展名跟流格式一致；
- **不要求**：弹幕录制、弹幕渲染、转码为 MP4。

参考项目 `BililiveRecorder-WPF-Portable` 是 WPF 发行包（无源码），只能参考行为：它按 FLV 标签级别写入、检测到断流后按新的分片续写、并在录制目录写 XML 侧车元数据；其分片策略基于"文件大小/时长上限 + 关键帧对齐"。

关键约束：**不转码** ⇒ 不能借助 ffmpeg 的 mux 能力重写时间戳与封装，必须自己按容器格式写字节。

## 决策

### 1. 支持两种容器：`FlvHttp` 与 `HlsTs`

| 输入格式 | 录制实现 | 产物扩展名 |
|---|---|---|
| `FlvHttp`（HTTP-FLV） | 解析 FLV 标签序列，去除 `onMetaData` 之前的垃圾，按标签原样写入；分片时重写 FLV Header + 复制首部脚本标签/`AVC sequence header` | `.flv` |
| `HlsTs`（HLS/TS 分片） | 按 m3u8 顺序拉取分片，剥离 m3u8 封装直接追加 188 字节 TS 包流（需处理跨分片续包） | `.ts` |
| `HlsFmp4`（fMP4） | **首版不支持**：fMP4 分片需要重写 `moof`/`mdat` 与初始化段，风险高、收益低；返回 `NotSupported` 并提示用户改用 Web 播放或 mpv 录制 | — |
| `Rtmp` | **不支持**：BCL 无 RTMP 客户端，引入第三方库违反依赖约束 | — |

> 抖音/B站的 HTTP-FLV 覆盖了绝大多数录制场景；虎牙同时给出 FLV 与 HLS，优先选 FLV。

### 2. 不转码、不改写载荷（可验证的硬约束）

- 代码中**禁止**出现视频/音频编码器调用（无 `ffmpeg`、无 `libx264`、无 `aac`），仅做字节搬运与容器头部处理。
- 校验手段：`Recording/Streams` 下只允许 `Stream`/`FileStream`/`BinaryReader` 操作；`Tests` 中断言"录制 1MB 输入得到的输出与输入载荷逐字节一致（FLV 场景比较标签区间）"。
- 唯一允许的改写：FLV 分片起始处写入新的 9 字节 Header + 4 字节 `PreviousTagSize0`，以及复制必要的首部脚本标签；TS 分片不做任何改写（TS 天然可连接）。

### 3. 分片策略

`SegmentPolicy`（可配置，全部集中定义，禁止魔法数字）：

| 配置项 | 默认 | 取值范围 | 说明 |
|---|---|---|---|
| `SegmentMaxBytes` | 1 GiB | 64 MiB ~ 16 GiB | 达到上限后在**下一个视频关键帧**处切分 |
| `SegmentMaxDuration` | 30 分钟 | 1 ~ 480 分钟 | 达到上限后同样在下一个关键帧处切分 |
| `SegmentMinBytes` | 8 MiB | — | 防止"刚开播就切出一堆小文件" |
| `SplitOnKeyFrameOnly` | true | — | FLV 必须按关键帧；TS 按分片边界 |
| `FileNameTemplate` | `{anchor}-{roomId}-{startTime}-{index}` | — | 见下 |

- **FLV 关键帧判定**：`VideoTag`（tagType=9）且 `AVCPacketType == 1`，且首字节低 4 位 `FrameType == 1`（keyframe）。切分点必须在**该帧的 tag 起始处**，保证新分片首帧可解码。
- **FLV 分片头**：新分片写入
  1. Header：`FLV\x01`、flags（保留 hasVideo/hasAudio 位）、`0x00000009`；
  2. `PreviousTagSize0 = 0`；
  3. 缓存的 `onMetaData` 脚本标签（tagType=18，首标签）；
  4. 缓存的 `AVC sequence header`（`AVCPacketType == 0`）与 `AAC sequence header`（`AACPacketType == 0`）。
- **时间戳重定基**：分片内时间戳统一减去分片首帧时间戳（保持相对连续性），并把相对偏移写回 tag 头（3 字节 + 扩展字节）。这样每个分片可独立播放。**这是对载荷之外唯一的时间戳改写，且不触碰编码数据**。
- **TS 分片**：以 m3u8 的分片为切分单位，累计字节/时长达到阈值时在分片边界切分；不做时间戳重定基（TS 播放器从 `PCR` 与 PTS 自行对齐），分片直接以 `.ts` 保存。

### 4. 断流重连

```
连接 → 读取 → [断流/超时/EOF] → 等待退避 → 重连(重新解析候选或复用原地址)
     → 成功且 PID/编码一致 → 追加到同一分片（FLV 允许，TS 允许）
     → 重连超过上限 → 结束本次录制会话，写元数据 summary
```

- **断流判定**：`ReadAsync` 返回 0（EOF）或连续 `StallTimeoutSeconds`（默认 12 秒）无字节到达。
- **重连退避**：`2s, 4s, 8s, 15s, 30s`（上限 30 秒），最多 `MaxReconnectAttempts = 8` 次；每次重连前重新校验 URL 有效期，过期则回调 `IRoomResolver` 重新解析（最多 3 次，与播放侧一致）。
- **关键帧一致性**：重连后若检测到 `SPS/PPS` 变化（FLV `AVC sequence header` 内容不同），**必须切分新分片**（编码参数变化不能混在同一文件），并在元数据中记录 `codecChangeAt`。
- **不无限重试**（`CLAUDE.md` 红线 7）：重连次数与总时长（默认 6 小时）双上限，任一触发即结束会话并写 `Info` 日志。

### 5. 元数据记录

每次录制会话在输出目录写一份侧车文件 `{anchor}-{roomId}-{startTime}.meta.json`（UTF-8，`System.Text.Json`，`WriteIndented`）：

```json
{
  "schemaVersion": 1,
  "platform": "bilibili",
  "roomId": 123456,
  "anchor": "主播名",
  "title": "直播标题",
  "category": "分区",
  "startedAtUtc": "2025-02-14T12:00:00+00:00",
  "endedAtUtc": "2025-02-14T13:30:00+00:00",
  "durationSeconds": 5400,
  "format": "flv-http",
  "codec": "avc",
  "totalBytes": 3221225472,
  "reconnectCount": 2,
  "stopReason": "user-stopped",
  "segments": [
    { "index": 0, "fileName": "主播名-123456-20250214-120000-000.flv", "bytes": 1073741824, "durationSeconds": 1800 }
  ]
}
```

- 敏感信息（签名 URL、Cookie）**不写入**；URL 只以 `UrlFingerprint`（长度 + SHA256 前 8 字节）形式记录。
- 元数据在会话结束时原子写入（临时文件 + `File.Move(overwrite: true)`）；进程崩溃时保底：每 `MetadataFlushSeconds = 30` 秒增量刷新一次 `segments`。

### 6. 文件命名

`{anchor}-{roomId}-{startTime}-{index}{ext}`

- `anchor`：主播名，过滤非法文件名字符（`Path.GetInvalidFileNameChars()` + `.`/` ` 归一化），长度截断 40 字符，全空时用 `unknown`。
- `startTime`：`yyyyMMdd-HHmmss`（**本地时间**，便于用户查找；`meta.json` 内同时记录 UTC）。
- `index`：3 位零填充，从 `000` 递增。
- 文件名冲突时追加 `-1`/`-2` 后缀（`FileNaming.ResolveUniquePath`）。
- 输出目录：`{config.recording.outputDirectory}\{platform}\{anchor}\`，默认 `%USERPROFILE%\Videos\StreamPilot`。

### 7. 与播放解耦

- 录制是**独立的第二条连接**：Web 播放与录制各自拉流，互不干扰（需求明确"Web 端与 mpv 端互不关联"，录制同理）。
- 因此录制不共享播放侧的 WebView2 缓冲区，也不依赖桥接服务存活。
- 同一房间允许同时录制与播放；同一房间**禁止重复录制**（`RecordingCoordinator` 按 `(platform, roomId)` 去重并在 UI 提示）。

## 影响

### 正面

- 完全自研、零转码，CPU 占用接近磁盘写入速度；产物与平台原始流一致，便于后续用 mpv/ffmpeg 自行处理。
- 分片可独立播放（FLV 新分片带 Header + 序列头 + 时间戳重定基）。
- 元数据完整记录主播名/房间号/标题/开播时间/时长，满足需求。

### 负面 / 风险

- fMP4 与 RTMP 不支持，属于已知限制，需在 `README` "已知限制"中说明。
- FLV 时间戳重定基在极端情况下（时间戳越过 24 位扩展边界）需要正确处理扩展到 32 位；已通过 `FlvTimestamp.Read/Write` 单元测试覆盖边界值（`0x7FFFFF`、`0xFFFFFF`、`0x1000000`）。
- 断流频繁时会产生较多分片，通过 `SegmentMinBytes` 与"编码参数变化才强制切分"缓解。

## 后续

- 若需要 fMP4 录制，需要引入 ISO-BMFF 分片重写能力（工作量约等于一个小型 muxer），必须先修订本 ADR 并评估依赖。
- 若需要"断流后自动合并分片"，属于后处理（可用 ffmpeg concat），不在首版范围内。
