## 0. 背景与目标

v0.2.1 已解决「收不到 4K/HDR」「mpv 播 HEVC 收不到数据」两个阻塞性问题。v0.2.2 定位为**一次较大整改**，目标：

1. 播放器 UI 从「控件堆叠」升级为「主次分明的沉浸式播放器」；
2. 补齐直播播放器最核心的缺失能力——**实时弹幕**；
3. 在合规红线内拓展功能（自动录制、开播提醒等）；
4. 借鉴 `LinkFlow-Plugin` 中确有价值的部分，但**不引入账号侧能力**（登录、领取、动态订阅）。

**非目标（明确不做）**：弹幕发送、账号登录、任何形式的风控绕过、指纹伪造。

## 1. 播放器 UI 重新设计

### 1.1 现状问题（基于代码与实测文档）

| 问题 | 证据 | 影响 |
|------|------|------|
| 控制条 9 个控件挤一行 | `docs/architecture/playback-strategy.md` §10.1.1：1024px 起换行，480px 时 3 行 | 窄窗口/小屏体验差 |
| 三个下拉同权重 | `#targetSelect` / `#lineSelect` / `#qualitySelect` 样式完全一致 | 用户分不清「画质」与「追帧档位」主次 |
| 状态行信息密度高 | `播放中 · 318 ms（极限追帧 250 ms）` | 与控件混排，视觉噪音 |
| 空态单调 | `#hint` 居中一行「等待直播源」 | 首屏缺乏引导 |
| 左侧面板四卡片平铺 | `MainWindow.xaml`：预设 → 直播源 → 当前直播 → 录制 | 入口分散，需要滚动 |
| 无弹幕区 | 全项目无 `danmaku` 代码 | 核心功能缺失 |
| 主题硬编码 | `player.html` CSS 与 XAML 资源各自维护色值 | 无法统一改主题 |

### 1.2 设计方向

#### A. 控制条从「一行堆叠」改为「主控层 + 参数层」

```
┌─────────────────────────────────────────────────────────────┐
│  ▶  00:32 / LIVE    音量 ▭    [弹幕]   [画质 4K]  [全屏]   │  ← 主控层（常驻）
├─────────────────────────────────────────────────────────────┤
│  线路：主线路 ▾   追帧：250ms ▾   更多 ▾                    │  ← 参数层（可收起）
└─────────────────────────────────────────────────────────────┘
```

- **主控层**：播放/暂停（**合并为单键**，图标随状态切换）、音量（滑条 + 静音图标）、弹幕开关、画质（当前档位常显）、全屏；
- **参数层**：线路、追帧档位、追帧开关（「追帧 / 停止追帧」合并进下拉）、更多；
- **自动隐藏**：播放中鼠标静止 3 秒隐藏两层，移动即显（全屏模式必须）；
- **保留旧布局开关**：设置里提供「紧凑控制条（旧版一行）」以照顾习惯用户。

预期收益：主控层控件从 9 个降到 5 个，1280px 下不再换行；参数层点击才展开。

#### B. 状态行与提示分离

- 状态行精简为 `播放中 · 318 ms`（追帧状态移到「追帧」下拉的当前值里，不再重复）；
- **缓冲健康度色条**：状态行左侧 3px 竖条，绿（<1s）/黄（1–3s）/红（>3s 或停滞）；
- **错误提示改 toast**：右下角浮层，3 秒自动消失，不再长期占用状态行（保留 `host-status` 的 6/12/20s 分级作为兜底）。

#### C. 视觉体系

- 抽出 **design token**：`--sp-color-*` / `--sp-radius-*` / `--sp-space-*` / `--sp-font-*`，播放页与 XAML 资源共用一套命名；
- 支持**深色/浅色主题**（跟随系统，`prefers-color-scheme` + XAML 的 `ThemeMode`）；
- 弹幕层预留右侧 0–320px 区域。

#### D. 左侧面板

- 四卡片改为 **Tab 切换**：`预设 | 直播源 | 录制`，「当前直播」信息收进顶部常驻条（主播/标题/开播状态/在线人数）；
- 面板可折叠（点击拖拽边缘或快捷键），把宽度让给画面。

### 1.3 改动范围

- `Web/player.html`：控制条 DOM/CSS、状态行、自动隐藏、弹幕层
- `Web/player-core.js`：状态行纯函数（`formatPlaybackStatusText` 等）、新增控件常量
- `src/StreamPilot.App/Views/MainWindow.xaml`：左侧 Tab 化、折叠
- `src/StreamPilot.App/Resources/`：主题资源、deep/light 配色
- `tests/web/player-core.test.js`：状态行断言、控件顺序断言更新
- `docs/architecture/player-message-contract.md`：如新增控件涉及消息，同步更新

### 2.1 优先级矩阵

| 优先级 | 功能 | 用户价值 | 实现成本 | 合规风险 | 说明 |
|--------|------|----------|----------|----------|------|
| **P0** | 实时弹幕（开关 + 展示） | 高 | 高 | 低（只读） | 第 3 节详述 |
| **P0** | 控制条/面板重构 | 高 | 中 | 无 | 第 1 节 |
| **P0** | 自动录制（开播即录） | 高 | 低 | 无 | 录制模块已有，加「订阅预设 + 开播检测」即可 |
| **P1** | 批量查询直播状态 | 中 | 低 | 无 | 借鉴 LinkFlow 的 `getRoomInfobyUids` |
| **P1** | 开播系统通知 | 中 | 低 | 无 | 预设状态轮询 + Windows Toast |
| **P1** | mpv 画质/线路指定 | 中 | 低 | 无 | 当前 mpv 固定取第一个候选 |
| **P1** | 播放统计（时长/峰值码率/丢帧） | 低 | 低 | 无 | 已有遥测数据，落地成面板 |
| **P2** | 多房间同时观看（分屏） | 高 | 很高 | 无 | 需重构会话模型 |
| **P2** | 弹幕发送 | 中 | 中 | **高（红线 3）** | 需登录态 + 风控，**暂不纳入** |
| **P2** | 主播信息面板（粉丝/分区） | 低 | 中 | 低 | 需 WBI 签名（LinkFlow 有参考） |

### 2.2 优先级依据

- **P0** = 用户明确提出 + 现有架构可支撑（弹幕除外，需新建子系统）；
- **P1** = 价值明确、成本低、互不阻塞；
- **P2** = 需要架构级改动或触碰红线，留到后续版本单独评估。

## 3. 实时直播弹幕开关设计

### 3.1 技术前提（B站为例）

弹幕是一条**独立的实时流**，与视频流无关，协议要点：

| 环节 | 接口/协议 | 说明 |
|------|-----------|------|
| 获取连接凭证 | `GET https://api.live.bilibili.com/xlive/web-room/v1/index/getDanmuInfo?id={roomId}&type=0` | 返回 `token` 与 `host_list`（多个 wss 节点） |
| 建立连接 | `wss://{host}:{wss_port}/sub` | WebSocket |
| 认证包 | op=7，body 为 JSON `{uid, roomid, protover:3, platform:"web", type:2, key:token}` | 连接后立刻发送 |
| 心跳 | op=2，每 30 秒 | 双向保活 |
| 消息包 | 16 字节头（`packet_len(4) + header_len(2) + protover(2) + operation(4) + sequence(4)`） | `protover=3` 时 body 为 **Brotli 压缩**，解压后可能是多个子包 |
| 弹幕消息 | op=5，body 为 JSON 数组 | 需按 `cmd` 字段分类（`DANMU_MSG` / `SEND_GIFT` / `INTERACT_WORD`…） |

**依赖评估（遵循 CLAUDE.md 依赖管理）**：

- Brotli：`.NET` 内置 `System.IO.Compression.BrotliStream` ✅ 无需第三方
- WebSocket：`.NET` 内置 `System.Net.WebSockets.ClientWebSocket` ✅
- **零新增第三方依赖**，不需要新 ADR（如后续引入需补 ADR）

### 3.2 分层设计（遵循 CLAUDE.md 架构边界）

| 层 | 新增内容 | 职责 |
|----|----------|------|
| `StreamPilot.Core` | `DanmakuMessage` 模型、`IDanmakuClient` 接口、`DanmakuOptions` 配置 | 契约与模型，**不引 UI** |
| `StreamPilot.Parsers` | `BilibiliDanmakuProtocol`（纯函数：封包/解包/Brotli 解压/JSON 解析） | 协议编解码，**可用单元测试全覆盖** |
| `StreamPilot.App` | `BilibiliDanmakuClient`（`ClientWebSocket` + 重连 + 心跳）、`DanmakuCoordinator` | 连接生命周期，异步不阻塞 UI |
| `StreamPilot.App`（ShellViewModel） | 开关状态、连接状态、**批量节流转发** | 状态管理与转发 |
| `Web/` | `danmaku-renderer.js`（轨道分配 + DOM 池）+ `player.html` 的 `#danmakuLayer` | 渲染 |

**关键决策：WebSocket 客户端放在 App 层，不走 Bridge。**
理由：
1. 复用现有 `postMessage` 消息契约（App ↔ 播放页），**不新增网络端点、不扩大桥接攻击面**；
2. 弹幕是无鉴权风险的外部数据，经 App 层过滤后转发，无需暴露 HTTP 端口；
3. Bridge 层职责保持「中继 + mpv 启动」不变，符合 ADR 0005/0007 的边界。

**转发策略**：App 层按 **100 ms 批量**聚合弹幕，通过 `danmaku` 消息一次性下发（避免每条一条消息压垮 WebView2 消息通道）。

### 3.3 开关逻辑（三级）

| 级别 | 位置 | 默认 | 持久化 | 作用 |
|------|------|------|--------|------|
| **L1 全局开关** | 设置 → 播放 | 开 | ✅ `config.json` | 关闭后不建立任何弹幕连接（彻底关闭） |
| **L2 会话开关** | 播放页主控层「弹幕」按钮 | 开（记住上次） | ➖ 运行时 | 只控制**当前会话是否显示**，连接可保留 |
| **L3 类型过滤** | 弹幕设置（长按/右键 L2 按钮） | 只看弹幕 | ✅ | `只有弹幕` / `弹幕+礼物` / `全部（含进场）` |

### 3.4 状态机

```
                    ┌──────────────┐
     L1 关闭 ──────▶│  Disabled    │  不建连、不占资源
                    └──────────────┘
                            │ L1 开 && 有播放会话
                            ▼
                    ┌──────────────┐   getDanmuInfo 失败/ws 连不上
                    │  Connecting  │──────────────▶ Failed（重试≤3，指数退避 1/2/4s）
                    └──────────────┘                      │
                            │ 认证成功                       │ 用户点「重试」
                            ▼                              │
        ┌──────────────────────────────────┐               │
        │           Connected              │◀──────────────┘
        │  Visible  ──(L2 关)──▶  Hidden   │  Hidden：保持连接、不渲染
        └──────────────────────────────────┘
                            │ 播放会话停止（request-stop / 切房间 / 关窗）
                            ▼
                    ┌──────────────┐
                    │  Disconnected │  释放 WebSocket
                    └──────────────┘
```

**生命周期绑定**：

| 事件 | 弹幕行为 |
|------|----------|
| `play` 下发（新会话） | 若 L1 && L2 开 → 启动连接 |
| `request-stop` / 宿主停止 | 断开连接、清空缓冲 |
| 切画质 / 换线路（同房间新会话） | **不断开**（房间未变），仅重置渲染缓冲 |
| 暂停 / 继续 | **弹幕继续滚动**（直播语义：弹幕是实时聊天，不随视频暂停）——见 §9 待确认项 |
| 切换到另一个房间 | 断开并用新 `roomId` 重连 |

### 3.5 状态管理

**配置层（`StreamPilotOptions` 新增 `DanmakuOptions`）**：

```text
DanmakuOptions
├── Enabled              : bool   // L1 全局开关，默认关
├── Visible              : bool   // L2 上次可见性，默认 true
├── Filter               : enum   // 类型过滤：ChatOnly / WithGift / All
├── DisplayMode          : enum   // 显示模式：Compact（精简）/ Full（完整）
├── BlockedKeywords      : list   // 屏蔽词（文本包含即不显示，不区分大小写）
├── MergeDuplicates      : bool   // 是否合并重复弹幕，默认 true
├── MergeWindowSeconds   : int    // 合并窗口秒数，默认 3
├── Opacity              : double // 不透明度，默认 0.9
├── FontSize             : int    // 字号，默认 24
├── SpeedSeconds         : int    // 横穿屏幕耗时，默认 8
└── MaxOnScreen          : int    // 同屏上限，默认 60
```

**三项内容控制的分工（互不重叠）**：

| 配置 | 作用维度 | 说明 |
|------|----------|------|
| `Filter` | **显示哪些类型** | ChatOnly 只弹幕 / WithGift 含礼物 / All 含进场与系统 |
| `DisplayMode` | **单条显示多少信息** | Compact 只显示「昵称 + 文本」；Full 额外显示粉丝牌、等级、颜色 |
| `BlockedKeywords` | **内容屏蔽** | 文本包含任一关键词即丢弃（忽略空串与纯空白，不区分大小写） |
| `MergeDuplicates` + `MergeWindowSeconds` | **重复抑制** | 相同文本在窗口内合并为一条并累加次数（如 `666 ×15`） |

> 精简版与完整版**不是**类型过滤的替代：前者控制单条信息量（视觉密度），后者控制消息种类。
> 两者可自由组合，例如「完整版 + 只看弹幕」= 显示粉丝牌与颜色、但不显示礼物和进场。


**运行时状态（`ShellViewModel`，不入盘）**：

```text
DanmakuConnectionState : Disconnected / Connecting / Connected / Failed
DanmakuReceivedCount   : long   // 本次会话累计，用于诊断
DanmakuDroppedCount    : long   // 因限流丢弃数
```

**环形缓冲**：App 层保留最近 **500** 条（供播放页重连补发/诊断），超出淘汰最旧，内存上限约 100 KB。

### 3.6 新增消息契约（必须同步更新 `player-message-contract.md`）

| 方向 | type | 字段 |
|------|------|------|
| 宿主 → 页面 | `danmaku` | `items[]{ id, type, user, text, color, ts, guardLevel, medal }`（批量） |
| 宿主 → 页面 | `danmaku-state` | `state`（connected/failed/hidden…）、`enabled`、`receivedCount` |
| 页面 → 宿主 | `danmaku-toggle` | `visible`（bool） |
| 页面 → 宿主 | `danmaku-retry` | 用户在 Failed 状态点重试 |

**兼容性**：全部为**新增 type**，旧版页面按未知 type 记 Warn 后忽略，旧版宿主不下发时页面显示「弹幕不可用」占位——符合契约 §4 的向后兼容要求。

### 3.7 渲染设计

- `#danmakuLayer` 绝对定位于 `#stage`，`pointer-events: none`（不挡鼠标）；
- **轨道分配**：按屏高划分为 N 条轨道（字号 24 时约 12 条），新弹幕选「最早空闲」的轨道；同轨最小间隔 = 弹幕宽度 / 速度，避免追尾；
- **DOM 复用池**：最多 `MaxOnScreen` 个节点循环复用，超出直接丢弃（计入 `DanmakuDroppedCount`）；
- **限流**：单帧最多插入 8 条，超出排队（队列上限 200，溢出丢弃）；
- **样式**：白字 + 1px 黑描边（HDR 画面可读），支持 `Opacity` / `FontSize` / `SpeedSeconds`。

### 3.8 使用场景

| 场景 | 行为 |
|------|------|
| 看直播（主场景） | 弹幕与画面同步滚动，鼠标不动时随控制条一起隐藏，画面纯净 |
| 专注画面 | 点「弹幕」按钮一键关闭（Hidden），连接保留，再点秒开 |
| 热门大主播（弹幕刷屏） | 超过 `MaxOnScreen` 自动丢弃低优先级消息（礼物/进场最先丢），保弹幕 |
| 弱网/弹幕连接失败 | 顶部一角显示「弹幕连接失败 · 重试」，**不影响视频播放** |
| 多平台 | v0.2.2 只做 B站（协议最明确）；抖音/虎牙/斗鱼/YY/Bigo 弹幕协议在 P1 逐个补，接口预留 |

## 4. LinkFlow-Plugin 代码分析与采纳评估

### 4.1 项目定位（重要前提）

`LinkFlow-Plugin` 是 **Yunzai/Koishi 机器人插件**（`index.js` + `guoba` 配置面板 + `package.json`），能力集中在**账号侧运营**：

| 模块 | 行数 | 职责 |
|------|------|------|
| `model/BiliClient.js` | 390 | HTTP 客户端、WBI 签名、激励领取、动态订阅 |
| `model/BiliFingerprint.js` | 317 | 浏览器指纹 + MurmurHash3（`buvid_fp`） |
| `model/BiliTicket.js` | 52 | `bili_ticket` 风控凭证 |
| `model/LiveApi.js` | 86 | 直播间信息查询（含批量） |
| `modules/BiliLogin.js` | 94 | 扫码登录 |
| `modules/BotCookie.js` | 501 | Cookie 池管理 |
| `apps/livepush.js` | 268 | 开播订阅推送（cron 轮询） |
| `apps/incentive.js` | 455 | 激励/红包领取 |
| `apps/dynamic.js` | 237 | 动态订阅 |

**结论：与 StreamPilot（拉流/播放/录制）的重合面很小，且核心能力集中在「需要登录态」的方向，与 StreamPilot 的「只读播放器」定位冲突。**

### 4.2 逐项评估

| 模块 | 能力 | 采纳 | 理由 | 接入方式 |
|------|------|------|------|----------|
| `LiveApi.getRoomInfobyUids` | 批量查询直播状态（POST `get_status_info_by_uids`） | ✅ **采纳（P1）** | StreamPilot 预设「刷新状态」目前逐房间请求，N 个预设 = N 次请求；批量接口一次查完，显著降请求数 | `BilibiliParser` 新增 `ResolveRoomsStatusAsync(IReadOnlyList<string> roomIds)`；`PresetStore`/`PresetItemViewModel` 刷新时改调批量 |
| `apps/livepush.js` 的状态机 | 开播状态变化检测（0/1/2）+ 轮询节奏 | ✅ **采纳思路（P1）** | 自动录制与开播提醒都需要「只在状态变化时动作」，避免每次轮询都重复通知 | 不复制代码（Node→C#），按其「上次状态 vs 本次状态」比对模型实现 `PresetStatusPoller` |
| `BiliClient.getWebSign`（WBI） | WBI 签名（MD5 + `MIXIN_KEY_ENC_TAB`） | ⚠️ **储备（P2）** | 直播接口不需要 WBI；只有「主播信息面板（粉丝数/分区）」这类空间接口才需要 | 若做 P2 信息面板，在 Core 层新增 `BiliWbiSigner`（纯函数，可单测） |
| `BiliTicket` | `bili_ticket`（HMAC-SHA256） | ⚠️ **暂不采纳** | 直播接口当前无需该凭证；引入属于「增强风控兼容」，与红线 3 边界需单独论证 | 不接入；如未来确需，必须先补 ADR |
| `BiliFingerprint`（`buvid_fp`） | 伪造 33 维浏览器指纹 | ❌ **不采纳** | 这是典型的**指纹伪造/反爬对抗**，直接触碰 `CLAUDE.md` 红线 3「禁止绕过平台风控」 | 不接入 |
| `modules/BiliLogin.js` | 扫码登录 | ❌ **不采纳** | 播放器不应管理账号登录态；Cookie 由用户手动填入（现有设计） | 不接入 |
| `modules/BotCookie.js` | Cookie 池（多账号调度） | ❌ **不采纳** | 面向机器人多账号场景，播放器无此需求 | 不接入 |
| `apps/incentive.js` | 激励/红包领取 | ❌ **不采纳** | 与播放器无关 | 不接入 |
| `apps/dynamic.js` | 动态订阅 | ❌ **不采纳** | 与播放器无关 | 不接入 |
| **弹幕** | — | ❌ **无此能力** | 全项目 `danmaku`/`websocket` 命中 **0** | 弹幕必须按第 3 节自研 |

### 4.3 重点结论

1. **唯一有直接工程价值的可采纳项**：批量查询直播状态（`getRoomInfobyUids`）与「状态变化才动作」的轮询模型；
2. **弹幕不能从 LinkFlow 搬**——它没有 WebSocket/弹幕代码，需按 B站官方协议自研（第 3 节）；
3. **三类能力明确拒绝**：指纹伪造、扫码登录、Cookie 池——均与「只读播放器 + 不碰风控」的定位冲突；
4. 语言与运行时不同（Node.js vs .NET），任何采纳都是**思路/协议级借鉴 + C# 重写**，不存在直接拷代码。

## 6. 潜在风险

### 6.1 技术风险

| 风险 | 等级 | 缓解 |
|------|------|------|
| B站弹幕协议变更（Brotli/字段） | 中 | 协议解析集中在 `BilibiliDanmakuProtocol`（纯函数 + 单测），变更只改一处；解析失败降级为「弹幕不可用」，不影响视频 |
| 热门主播弹幕刷屏导致卡顿 | 中 | 限流（单帧 8 条）+ 同屏上限 60 + 队列溢出丢弃 + 低优先级先丢 |
| WebSocket 长连接不稳定 | 中 | 心跳 30s、重连上限 3 次、指数退避、失败不影响播放 |
| 弹幕在 UI 线程处理阻塞 | 中 | 全部异步 + 100ms 批量；遵循 CLAUDE.md「禁止 UI 线程阻塞」 |
| 消息契约变更破坏旧版 | 低 | 只新增 type，不改既有字段；按契约 §4 向后兼容 |

### 6.2 合规风险（红线相关，必须评审确认）

| 项 | 结论 |
|----|------|
| 弹幕**只读展示，不发送** | ✅ 规避红线 3（发送需登录+风控） |
| 不采集/不上传任何用户数据 | ✅ 弹幕仅内存缓冲，不落盘（除诊断计数） |
| 不引入指纹伪造 | ✅ 明确拒绝 `BiliFingerprint` |
| 不引入账号登录 | ✅ 保持用户手动填 Cookie 的现有模式 |
| 弹幕连接使用 `getDanmuInfo`（公开接口 + 现有 Cookie） | ✅ 属正常客户端行为，非绕过 |

### 6.3 产品风险

| 风险 | 缓解 |
|------|------|
| UI 大改导致老用户不适应 | 提供「紧凑控制条（旧版）」开关；分两阶段发布（先弹幕、后 UI） |
| 弹幕默认开启可能打扰 | 默认开，但提供一键关闭；首次启动弹一次「弹幕可关闭」提示 |
| 只有 B站有弹幕，其他平台空白 | 明确标注平台支持范围；其他平台协议在 P1 补 |

## 11. 负优化记录（实测后回退）

设计稿上的「改进」在真机使用中被证明是负担的，逐条记录并回退，避免下一版又改回去。

### 11.1 左侧面板 Tab 化（已回退）

| 项 | 内容 |
|----|------|
| 原设计 | §9 决策 5：预设 / 直播源 / 录制拆成三个 Tab |
| 问题 | 预设与直播源**各自只占半屏**，却要在两者之间来回切换；Tab 标题栏本身白占一行高度；三块内容在 900 高的窗口里本来就能一屏放下 |
| 结论 | **回退为单页平铺**（预设 → 直播源 → 录制），列表限高 240 px、整体保留滚动兜底；`ControlTabControl` / `ControlTabItem` 样式随之删除 |

### 11.2 面板折叠后恢复不了（已修复，修法二次调整）

| 项 | 内容 |
|----|------|
| 现象 | 点顶栏「◀」收起左侧面板后，再无任何入口可以展开 |
| 根因 | 恢复按钮浮在播放区左上角，而 **WebView2 是原生 HWND（HwndHost）**，永远画在 WPF 内容之上——按钮被盖住，既看不见也点不到（WPF + WebView2 的 airspace 问题） |
| 第一次修法（已回退） | 折叠后保留 **36 px 窄条**，恢复按钮放窄条里。能恢复，但一条空窄条既占地方又难看：顶栏标题被裁成半截（"Streaml"），窄条里孤零零一个「▶」 |
| 最终修法 | 折叠时左列**直接收成 0**（不留窄条）；恢复入口画在**播放页左上角**（「☰ 控制面板」，半透明白胶囊），点击发 `panel-expand` 让宿主展开。`Ctrl+B` 作为键盘兜底（WPF 侧 + 播放页各处理一次，因为 WebView2 聚焦时键盘事件到不了宿主） |

> 通用约束：**任何需要常驻可点的 WPF 控件都不能叠在 WebView2 之上**。
> 播放画面内的浮层（音量读数、空态提示、toast、面板恢复入口）一直由播放页自己在 HTML 里绘制，正是同一原因。

### 11.3 预设行的勾选框没有标签（已修复）

| 项 | 内容 |
|----|------|
| 原设计 | 预设行右侧只放一个裸 `CheckBox`（16 px 小方框），含义靠 `ToolTip` 说明 |
| 问题 | 不悬停就完全看不出它是什么——用户直接问"这个 ✔ 有什么用"；一个没有标签的方框还容易被误认为"选中行" |
| 结论 | 加文字标签「**自动录**」（`FontSize=13`，tooltip 写清"开播自动录制、下播自动停止"）；同排的「编辑 / 删除」按钮字号与内边距同步收紧（14→13、10,5→8,5），把宽度让给主播名 |
